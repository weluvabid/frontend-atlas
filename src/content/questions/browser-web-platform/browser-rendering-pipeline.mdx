## Short answer

A DOM or style change may invalidate style, layout, paint, or compositing state. The browser updates the necessary pipeline stages before presenting a frame; not every change requires every stage.

## Reason from first principles

Changing geometry commonly triggers layout and paint. Changing paint-only properties may skip layout. Compositor-friendly transforms and opacity can often update without repainting the whole page, but layer promotion has memory and scheduling costs.

## A concrete example

```css
/* Often composited without layout */
.card {
  transform: translateY(4px);
  opacity: 0.98;
}
/* Changes geometry and commonly requires layout */
.card {
  width: 24rem;
}
```

## Boundary cases to reason through

A style write followed by a geometry read can force synchronous layout because the browser must provide a current measurement. Avoid alternating reads and writes across many nodes. Paint invalidation and layer composition are implementation-dependent, so profile with the Performance panel and rendering diagnostics rather than inferring the pipeline from a CSS property name alone.

## Common misconception

“GPU accelerated” is not a blanket performance guarantee. Too many layers consume memory and can increase compositing cost.

## Why this matters in production

Batch DOM reads before writes, avoid layout thrashing, and profile the actual page. Optimize the bottleneck measured on target devices.
